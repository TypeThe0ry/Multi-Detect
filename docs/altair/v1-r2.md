# Altair v1-r2 配方

## v1-r1-a 结果与退步原因分析

v1-r1-a：热启动 r21id-r3 adapter，预设 A（q/v r16/a32），lr 3e-5（恒定，无衰减），1 epoch，
不开 `--balance`，数据 identity 22843 + planning 5460（身份占 81%）。4 项门槛全不过：

| 指标 | 现役 | v1-r1-a |
|---|---|---|
| confirm_recall | 0.709 | 0.632 |
| decision_accuracy | 0.854 | 0.803 |
| distractor_rejection | 1.000 | 0.974 |
| planning exact_sequence | 0.75 | 0.70 |

判断（按证据强弱）：

1. **不是「身份被稀释」，也不是类别偏置。** 身份数据占 81%，且从身份 adapter 热启动。
   若是偏向「全拒绝」，confirm_recall 会降但 distractor_rejection 会升；实际两者同时降，
   说明是整体判别质量下降（噪声/漂移），不是阈值位移。
2. **最可能原因：已收敛的身份 adapter 又被恒定 lr 3e-5 再训一整个 epoch（≈7000 步），且无 lr 衰减。**
   r21id-r3 本身是 5e-5 恒定 lr 训出来的，结尾点没有退火；再叠加 5460 行规划梯度，
   q/v r16 容量要同时装下两个任务，互相干扰，最终权重停在一个「噪声点」上。
3. **次要原因：容量。** 仅 q/v r16；规划（长 JSON 序列）与身份（短判决）目标差异大。
4. **planning 0.75→0.70 只是 20 题里少了 1 题**，在噪声内，不作为主要依据；
   但门槛容差 0.01 意味着「不许丢任何一题」，所以规划侧也要小心，不能靠少量 lr 变化碰运气。

## v1-r2 三条并行路线（互不依赖，空卡就排）

共同点：都以 `eval_altair.py` 的同一套门槛过关为准；固定翼两类必须保持 1.0。

### r2-a：低 lr 热启动（验证「lr 太高/漂移」假设，优先，GPU0）
同 v1-r1 数据集，lr 降到 1e-5，其它不变（预计 8~10 小时）。

```
R=/data/projects/Multi-Detect-env/Multi-Detect; cd $R
CUDA_VISIBLE_DEVICES=0 .venv-vlm/bin/python -m scripts.altair.train_altair --preset A \
  --dataset $R/artifacts/datasets/altair-v1-r1 --output $R/artifacts/models/altair-v1-r2-a \
  --accumulation 4 --epochs 1 --learning-rate 1e-5 --crop-policy candidate_zoom_v2 \
  --init-adapter $R/artifacts/models/slow-system-lora-v2-r21id-r3/adapter
bash scripts/altair/run_candidate_eval.sh $R/artifacts/models/altair-v1-r2-a/adapter v1-r2-a
```

### r2-c：缩短暴露的热启动（降低漂移总量，约一半时间，有空卡就跑）
身份子采样到 11000（热启动本来就已学过身份），规划全量 5460，lr 1.5e-5。
身份：规划约 2:1，步数约 4100。

```
PYTHONPATH=$R/src:$R .venv-vlm/bin/python -m scripts.altair.build_dataset \
  --source identity=$R/artifacts/r21id-r3/pipeline/r15-sft:11000 \
  --source planning=$R/artifacts/scratch/cx-planner-round/r24/dataset:5460 \
  --prefix-ids --crop-policy candidate_zoom_v2 --leak-scope same-source --on-leak drop \
  --seed 7 --output $R/artifacts/datasets/altair-v1-r2c
CUDA_VISIBLE_DEVICES=<空卡> .venv-vlm/bin/python -m scripts.altair.train_altair --preset A \
  --dataset $R/artifacts/datasets/altair-v1-r2c --output $R/artifacts/models/altair-v1-r2-c \
  --accumulation 4 --epochs 1 --learning-rate 1.5e-5 --crop-policy candidate_zoom_v2 \
  --init-adapter $R/artifacts/models/slow-system-lora-v2-r21id-r3/adapter
bash scripts/altair/run_candidate_eval.sh $R/artifacts/models/altair-v1-r2-c/adapter v1-r2-c
```

### r2-b：冷启动更大容量（验证「容量」假设，成本最高，最后排）
预设 C（q/k/v/o + MLP，r32/a64），冷启动，用 v1-r1 数据集全量，lr 5e-5，1 epoch。

```
CUDA_VISIBLE_DEVICES=<空卡> .venv-vlm/bin/python -m scripts.altair.train_altair --preset C \
  --dataset $R/artifacts/datasets/altair-v1-r1 --output $R/artifacts/models/altair-v1-r2-b \
  --accumulation 4 --epochs 1 --learning-rate 5e-5 --crop-policy candidate_zoom_v2
bash scripts/altair/run_candidate_eval.sh $R/artifacts/models/altair-v1-r2-b/adapter v1-r2-b
```

## 判读与后续

- r2-a 过关 → 定 v1，lr 假设成立；r2-a 和 r2-c 都过，取指标更高者。
- r2-a/r2-c 身份都回到现役附近但规划仍丢题 → 规划侧是容量问题，转 r2-b。
- 三条都不过 → 保持现役，v1 改为「两个独立 adapter 按任务路由」的备选，
  不再强行合并（板载可用 llama.cpp 多 LoRA 热切换）。
- 固定翼新增样本与真实视频伪标签源，等采集完成再加进下一轮数据集，不和本轮混。
