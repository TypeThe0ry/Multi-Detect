## 以下为历史阶段：只接相机，尚未加载AI

## 已实现的两段接口

相机入口读取 Gazebo 实际传输的 RGB、传感器时间和来源记录。它核对原始像素、
画面顺序和时间，再把用户原文以及最多两张当前／过去画面送入共享 NavigationActor。
场景真值、姿态、GPS、深度、答案和来源文件名不混入模型消息；来源核验记录单独保存。
两帧超过原有输入预算时，只保留最新帧，不扩大预算或偷偷缩小原始来源画面。
这里的帧龄从采集主机收到来源帧开始计算，不是已验证的相机曝光到主机的总延迟；
传感器与主机时钟尚无完整映射。像素和来源哈希正确也不代表外部来源已被认证。

学习型动作后端读取同一个 Actor。它走视觉与文字的实际融合计算，再接保存的训练
归一化和动作头，输出四个行动分数、距离和转角。这里不生成回答文本，也不虚构
生成 token、置信度或固定的三米／三十度。选中动作的尺度非法时保留原数值并拒绝。
停止仍只是序列停止，不能冒充任务完成、返航或降落。

这两段组件不加载或认证模型，不拥有 PX4 发送权限。后续独占模型进程必须另行证明
加载的底座、LoRA、动作头、输入来源及运行期间参数确实与声明一致，并拥有超时退出门。
即使接口通过，也不代表模型质量合格。

## 软件验证与实际验证分开

根线程运行两组新测试，共 83 个小型 CPU fixture 通过；独立子智能体复核输入和输出。
这些测试检验像素／时间／身份／预算／异常处理，不是实际 Qwen 或 Gazebo 推理。
[软件回执](evidence/onboard-navigation-gazebo-shadow-components-software-20261008-r1.json)
保存最终文件身份；最后一次图像绑定校验也计入帧龄与截止时间，拒绝不消耗输入序号。
独立相机环境已安装并实际导入 NumPy、OpenCV 和 pymavlink，版本固定在
[相机环境清单](../configs/requirements-gazebo-navigation-capture-20261008-r1.txt)。
原有训练环境未改动。

原 Docker 采集入口没有向下转发高分辨率时钟，默认产生旧 monotonic 来源记录；
而新共享输入要求显式的 perf-counter 时钟身份。两个时钟不能因本机数值接近就改名。
本轮新增独占进程的只观察采集入口，限域传入同一个真实时钟实例，结束后恢复原调用。
它不是生产级公开时钟 API 或通用线程安全适配器；后续正式集成应增加显式时钟接口，
再重新锁定新执行来源。既有封存实验文件保持原样。

## 为什么现在不能接管飞行

稳定训练已完成，但整段路线留出的合法行动仅 46／208；质量门失败。
本轮只验证真实相机到共享输入的接线。模型接通后也先保留只观察模式，不能用一次
格式正确的动作、旧策略带飞或没有起飞的画面证明自主导航。

真实教师数据需新增来源／结果契约与三维行动覆盖；旧预计划位姿监督和四类小头
不能冒充升降、横移或受阻恢复。见[下一轮训练数据](onboard-navigation-gazebo-training-data-next.md)。

后续顺序是：实际来源闭合 → 精确候选只观察推理 → 原底座／旧 warm／候选公平对照 →
补三维多任务、变尺度与受阻恢复数据 → 未见场景闭环 → 合格后才允许受安全监督的飞行。
默认 r33、`0.3.0-pre.8`、Jetson／HIL／REAL／室外 GNSS／最终发布门均不因本轮接线改变。
