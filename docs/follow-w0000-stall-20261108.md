# gen_mov_w0000 PX4 位置时钟停滞离线分析（2026-11-08）

后续[只读时序复核](clock-stall-lifetime-attribution-20261108.md)发现：五份都有超过 50 秒的全部原始 MAVLink 空窗，首次 GDB 前 listener 反推的 PX4 hrt 也接近冻结值，随后在捕获期间恢复。本文的 Gazebo/IMU 进展取自 deadline 后恢复阶段，不能支持“静默期间仅位置流异常、全局时钟始终正常”的结论。场景对照与历史采样保留，现场归因以复核报告的时间边界和限制为准。

## 结论

我对 v2 的五份 `clock_stalled_alive` capture 分别运行了时间线分析和 capture 分类。它们没有重复 2026-11-07 r9r 记录到的 Gazebo `PublishStats` transport mutex 等待：按归档 GDB 文件重新绑定路径后，五份中 **0/5** 有 `publish_stats_mutex_wait`。三份 Gazebo runner 栈为 `Step`/`Step`，一份为 `Step`/`not_observed`，一份两次都没有可分类的 runner 栈。四份 capture 的 Gazebo clock 在探针窗口内前进；五份的 PX4 IMU（`sensor_combined`）与 `vehicle_status` listener 时间戳均前进。Gazebo paused 状态和 camera frame 进展仍为 unknown。

更准确的描述是：采集器在 MAVLink `LOCAL_POSITION_NED` 的 `time_boot_ms` 45 秒没有进展后报错，而不是证据已经证明 PX4 全局时钟或 Gazebo 仿真完全停住。四次最后完成的 onboard step 明确仍处于 `area_search`；第五次在 step 175 返回途中，之前的 `area_search` 已因 step budget 失败。**五次都没有证据表明已进入 `follow`。**

`gen_mov_w0000` 与 `gen_mov_w0002` 的移动目标、模型、插件、传感器声明和 driver 机制相同。主要差异是相同大小的轨迹平移：w0000 目标轨迹离 vehicle spawn 更远。当前假设是 w0000 的搜索/接近路径和持续 `set_pose` driver 调用，在宿主高负载时增加 PX4 位置遥测停顿的机会；证据不支持“固定 waypoint/collision 触发 Gazebo PublishStats 锁死”。这只是可检验假设，不是根因结论。

## 五份 capture 的时间线与任务阶段

表中“PX4 位置”是 failure snapshot 的 `pose.time_boot_ms` / capture 诊断中最后一次 `LOCAL_POSITION_NED` 进展；Gazebo 两个时刻是 watchdog 触发后的 `deadline` 与 `after_3s` 样本，不是已确定的 stall 起点。step 编号是未完成的请求；`steps.jsonl` 最后一条成功记录因此是前一号 step。

| 配置 / episode | 超时 step | 最后记录的 onboard 阶段 | PX4 pose / 最后进展（s） | Gazebo deadline → after_3s（s） | Gazebo runner 分类 |
| --- | ---: | --- | ---: | ---: | --- |
| fixed-camera / `6d19f0b0` | 96 | `area_search` | 400.048 / 406.320 | 416.500 → 418.740 | `step` / `step` |
| fixed-camera / `10e0b0ed` | 111 | `area_search` | 399.496 / 399.708 | 410.788 → 413.168 | `step` / `step` |
| fixed-camera retry / `f7cc935c` | 98 | `area_search` | 292.564 / 297.572 | 309.512 → unknown | `not_observed` / `not_observed` |
| gimbal / `51cf7021` | 120 | `area_search` | 459.520 / 466.764 | 475.568 → 477.548 | `step` / `not_observed` |
| gimbal retry / `74245a75` | 175 | `return_home` recovery；`area_search` 已以 `step_budget` 失败 | 623.952 / 629.736 | 638.784 → 640.568 | `step` / `step` |

`mission_summary.json` 在前四份将阶段完成状态保留为 unknown；与其对应的最后 `steps.jsonl` onboard label 均明确为 `area_search`。第五份的最后 label 是 `return_home`，summary 记录 `s1:area_search` 因 step budget 失败。没有一份记录 `follow` 已开始。failed step 本身没有成功后的 `obs_after` 或 action 记录，不能再从它推导更精确的飞行动作。

PX4 GDB 栈在四份中，首个样本出现 `pthread_cond_broadcast -> px4_clock_settime -> gz::transport::NodeShared::TriggerCallbacks/RecvMsgUpdate`，第二样本转到 `poll -> zmq_poll -> RunReceptionTask`；剩下一份首样本在 `pthread_mutex_lock` 的 `px4_clock_settime` 路径，第二样本出现 `pthread_cond_broadcast`。分析器对这些样本给出的只是单样本 callback-blocked candidate；五份的 `supports.callback_blocked` 和 `supports.px4_thread_block` 均为 false。gimbal retry 另有单个 `wkr_hrt` blocked candidate，未达到 capture 分类器的支持条件。这些短样本不能描述 45 秒窗口内的连续行为。

两份 retry-history 的 capture JSON 里 GDB 绝对路径仍指向原始 `episodes/episode-...`，而实际 GDB 文本位于对应 `retry-history/episode-...-<hash>/`。因此直接把这些 JSON 路径交给 capture CLI 会得到 `not_observed` 或空列表。上述栈比较是对只读 JSON 在内存中将路径重新指向同目录归档文本后运行同一 `analyze_capture()`；没有改写 artifact。fixed-camera retry 的实际 GZ GDB 文本也没有可识别的 `Step`/`PublishStats` frame（其中一次 GDB 超时），所以仍分类为 unknown，而非声称 runner 栈正常。

五份 `failure_snapshot` 的宿主负载快照均有压力背景：1 分钟 load average 为 160.23–574.15，CPU PSI `some avg10` 为 19.93–63.28%，memory PSI `some avg10` 为 0–82.04%。它支持负载可能参与，但单次压力快照无法指认 scheduler starvation 是直接原因。相机没有被 stall capture 探测；capture 后的 clock/listener 样本也不能证明 watchdog 窗口全程如何运行。

## world 与生成输入对照

`configs/scenarios/generated-movers/gen_mov_w0000.{scenario,runtime_input,truth,expectations}.json` 与 w0002 对照后，关键物理配置相同：两者都是红色 person，尺寸 `1×1×1.8 m`，`speed_mps=1` 的四边环形 trajectory，各边 12 m、每圈 48 s；vehicle spawn、零风、相同 runtime sensor declarations 和 expectations 相同。seed 与 world/target ID 随编号变化。

`world_gen.py::generate_mover_worlds()` 按 world index 平移轨迹中心。w0000 中心为 `(-18, 28) m`，waypoints 是 `(-24,22) → (-12,22) → (-12,34) → (-24,34)`；w0002 中心为 `(-4,10) m`，waypoints 是 `(-10,4) → (2,4) → (2,16) → (-10,16)`。因此初始 waypoint 到 vehicle spawn `(0,0)` 的距离分别约 32.6 m 和 10.8 m。两条路径形状、长度、速度和转角时刻相同，w0000 路径相对出生点更远。

两个 SDF 都只有 `ground_plane` 和一个静态 target box model，物理参数、scene/light 和唯一 `gz-sim-label-system` 插件相同。目标模型只含 visual，没有 actor element 或 collision geometry；它的 SDF 起始 pose 分别来自各自第一 waypoint。移动并非 SDF actor plugin 完成：collector 从 truth 中读取 trajectory，启动同一 `scripts/gz_mover_driver.py`，该 driver 订阅 `/clock` 并按 0.1 sim-second 周期请求 Gazebo `set_pose`。runtime input 两者都声明 front RGB、downward depth、MAVLink telemetry 三项；相机来自固定相机或 gimbal vehicle model overlay，两个 world 没有额外传感器。地图和 DEM 内容除 scenario ID 外相同。

五个 deadline Gazebo sim sample 对 48 s trajectory 周期取模后分别为 21.512、26.788、32.500、43.568、14.784 s；最近 waypoint 边界相差约 2.5–4.4 s，且落在不同边和不同拐点。它们不是同一个 loop/waypoint 时间。更重要的是这些采样在 45 s watchdog 后，不是 stall 起始时刻，故不能用这个接近关系证明 waypoint 触发故障。没有记录到 target collision；SDF target 没有 collision geometry。

失败 episode 没有落盘 mover driver log。现有正常结束的 w0000 log 有 4,713 条 set_pose 请求，其中 1,252 次返回失败；两个正常结束的 w0002 log 分别为 4,642 条中 1,214 次失败，以及 5,471 条中 1,588 次失败。三者中位 service latency 约 0.426–0.449 s，失败占比约 26–29%，没有显示 w0000 成功 run 独有的异常；这些完整 run 不能替代五个失败窗口中的缺失 driver log。

## 假设与最小 SITL 对照

优先验证“w0000 更远的 area-search/接近路径叠加 mover `set_pose` 服务调用，在宿主压力较大时让 PX4 位置遥测暂停；Gazebo physics 与部分 PX4 sensor/telemetry 时钟仍推进”。该假设与本次栈和阶段标签一致，但 target 的空间偏移、driver 服务调用和宿主运行负载仍是混杂因素；目前证据不足以断言 driver 是根因。单独的 trajectory waypoint 或 actor collision 解释缺乏支持。

`.tmp/jobs/42-w0000-stall-ab.sh` 安排一个串行 paired run：同一 fixed-camera airframe、同一 w0000 SDF/target 初始位置、任务文本、模型、180-step/2400-second envelope，各跑 1 个 episode。第一项使用原 moving truth；第二项在 `.tmp` 生成副本 truth，将 target 标为 stationary 并去掉 trajectory，所以 collector 不启动 mover driver，target 仍保留在 SDF 第一 waypoint 的静态位置。脚本重算临时 scenario channel hashes，不改源配置或产品代码；设置 `MULTIDETECT_SITL_SLOTS=3`、`--workers 1`，输出到新的 `artifacts/benchmarks/follow-w0000-stall-ab-<UTC>-<PID>/`。`--dry-run` 仅写 `.tmp`。

比较时以 `clock_stalled_alive` 是否重现、PX4 `LOCAL_POSITION_NED` 与 IMU/status 时间戳、Gazebo clock、两份 GDB stack 和 pressure 为主要观测。移动组复现而静止组不复现会支持 mover-driver/运动带来的负载贡献，但单对结果仍不足以证明根因；两组都出现相似位置遥测停顿会削弱“mover driver 是必要原因”；两组都完成则属于一次未复现，需重复配对。静止目标改变了 follow 任务语义，原 moving-distance/follow expectations 可能失败，因此它们不是该实验的通过指标。

该对照 job 尚未执行。没有修改 runtime timeout、lockstep、world control 或现有 artifacts；未运行 SITL、Docker、GPU 工作或下载。
