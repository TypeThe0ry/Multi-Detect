# OnboardAI live-loop integration audit — 2026-10-07

## Conclusion

The shortest route is a **new live OnboardAI runner that reuses the existing Gazebo capture, MAVLink lifecycle, VLM worker and continuation compiler**. Rebuilding flight control or another 40-feature policy is not necessary. The missing integration is concrete: the live acceptance runner instantiates the old ONNX provider; the new VLM worker and original-parent continuation host have no live flight call site. A real whole-sortie loop also needs a measured clearance producer, a verified replacement-parent chain and an independent bounded-wait/return supervisor.

This is a source audit, not a Gazebo flight, Jetson latency, model promotion or physical acceptance result. The product requirement remains arbitrary Prompt + continuing RGB/state/history → useful typed flight intent → PX4 execution → measured sensor feedback. The currently registered search template is a historical implementation, not the semantic boundary of the product. See [product goal](D:/Projects/Multi-Detect/docs/product-goals-and-roadmap.md).

## Can existing depth supply real 3D clearance?

Yes as a **measured local input**, not as a complete permission certificate. The [model SDF](D:/Projects/Multi-Detect/simulation/gazebo/models/x500_mono_cam/model.sdf) contains a co-located depth camera with 1280×960 R_FLOAT32 output, 30 Hz updates and approximately 99.7° horizontal field of view. The actual [depth contract](D:/Projects/Multi-Detect/scripts/gazebo_sensor_stream.py:473) binds RGB/depth sequence, stamps, intrinsics, payload SHA and optical-axis-Z distance semantics. The helper's dynamic depth association is causal with a 100 ms bound. The `gazebo_depth.py` introductory “future helper” comment is stale relative to this implemented transport.

The new producer should consume these depth bytes plus frame-bound pose/calibration, back-project `Z` with intrinsics, transform optical coordinates through the calibrated mount to NED/geodetic coordinates, and test a conservative 3D swept volume of the **actual compiled wire**, including altitude changes, acceptance/corner envelopes and finite loiter. Inflate for vehicle dimensions, GPS/pose/calibration uncertainty and measured delay. Bind the result to the current context/event, target, complete wire hash, exact source payloads and oldest contributing observation time. Invalid ranges, NaN/infinity, occlusion and unobserved cells remain unknown; SDF far clipping or an empty depth pixel is not “free space”. No world-object positions/truth masks may be fed to the VLM to fabricate this result.

A single forward camera cannot prove rear/upward space or an entire 25 m-radius loiter. For the first live experiment, use a separately authored bounded runtime whose route and finite dwell geometry are actually observable, or acquire additional actual sensor viewpoints. If coverage is insufficient, the compiler/admission must report that precise reason. A versioned measured local execution envelope may eventually replace an unnecessarily broad historical route assumption, but it requires an explicit monitored control design; do not weaken a sealed clearance claim merely to get a run through.

Gazebo's official rendering interface supports depth frames and RGB point-cloud callbacks, but this repository currently consumes the metric depth stream rather than a collision map. [Gazebo depth documentation](https://gazebosim.org/api/rendering/7/depth_camera.html). PX4's documented Collision Prevention acts in acceleration-based multicopter Position mode and blocks motion in uncovered directions; it is **not evidence that these AUTO.MISSION commands are collision-protected**. Do not assume `CP_DIST` silently supplies missing whole-route clearance. [PX4 Collision Prevention](https://docs.px4.io/main/en/computer_vision/collision_prevention).

## Smallest complete next implementation

1. **New live runner, not a new flight stack.** Add a separate entry point that reuses the existing capture/owned transport lifecycle and accepts verbatim `PromptEnvelope`. Construct `OnboardMultimodalInput` from actual RGB, source-bound telemetry and the execution ledger; use v2 serializer and one persistent worker. Keep YOLO as optional auxiliary perception rather than substituting its classes/colors for the RGB input. Keep unknown telemetry/range unknown.
2. **One receiver owner and one command writer.** The current flight observer and replacement wire cannot race to drain the same MAVLink connection. Add a bounded receive broker/lease: preserve original source/host receive timestamps and sequence, distribute immutable records to lifecycle/current context/episode collector, and route the exclusive replacement transaction through one writer. Upload/readback/resume must have their actual received evidence; successful send or callback return alone is not completion.
3. **Wire the first real continuation.** Live frame callback submits a source request without blocking telemetry. Poll complete results outside executor locks; reparse exact raw output, retain original source scope/time/target and rebase only against fresh actual execution state. Supply live original-parent/HOLD proofs and measured complete-wire clearance to `OriginalParentContinuationHost`. Ordinary new frames queue latest work; changed task/Prompt/scope/mission lineage or cancelled generation retire obsolete work. Pending inference produces no fake HOLD decision or Mission mutation.
4. **Second child is the indispensable repeated-loop test.** Extend parent binding to a verified `RESUMED` replacement chain rather than pretending the child has an ordinary `START_PERMITTED` journal. Require immutable predecessor admission/transaction/readback/wire/cursor identity, actual fresh mode/airborne evidence, same Prompt/task/vehicle/profile/home epoch, generation and one-use lineage. A cancelled/uncertain transaction must never become a parent or later resume. Acceptance requires two distinct model decisions, two actual in-air replacements, no extra TAKEOFF/LAND between them, and actual post-action pose/RGB change.
5. **Independent wait/return supervisor.** Run the bounded-wait/energy/return policy outside the VLM process and outside long upload/inference calls. Finite LOITER_TIME is not an implemented watchdog. Worker crash, expired input, exhausted return reserve, sensor loss, transaction uncertainty or operator cancellation need a declared measured HOLD/RTL recovery path with actual mode feedback and no contradictory later resume. Reuse lifecycle/energy safety facts; do not hardcode the semantic answer to every Prompt.
6. **Collect source→decision→executed action→feedback episodes.** Record exact Prompt/RGB/state/history request, raw/typed model output, accepted source/current identities, fixed target/effective plan, compiled wire, transaction generation, actual command/readback/cursor/mode, and subsequent measured trajectory/RGB/state over the action interval. Keep desired vs achieved movement separate. Reuse [raw position capture](D:/Projects/Multi-Detect/scripts/mission_position_capture.py:6) and [raw dynamics capture](D:/Projects/Multi-Detect/scripts/mission_dynamics_capture.py:10); receive time is not automatically source boot time. The existing exporter joins frame IDs to proposals, not all these action outcomes.

This is a coherent integration batch rather than more standalone receipt schemas: new live runner + shared receiver/writer ownership + measured depth producer + repeated-parent/watchdog coordinator + the causal episode join. Build the live shadow request/collector path first while a known baseline mission flies, then enable measured continuations only after the producer/lineage/supervisor path is in place. Shadow captures are already useful for observation-only temporal experiments; they must not be renamed reviewed action trajectories.

## Training and verification gates that measure the goal

The existing [staging builder CLI](D:/Projects/Multi-Detect/scripts/build_onboard_trajectory_staging.py:868) accepts RGB/depth/recording manifests plus source-bound airframe/task hashes. Its action labels remain missing and its output remains pending review. The [sortie exporter CLI](D:/Projects/Multi-Detect/scripts/export_onboard_sortie_transitions.py:364) accepts `--acceptance`, `--trajectory-staging`, `--output` and creates a proposal pending review. Use fresh output paths: neither operation turns model decisions into independently correct expert actions.

Evaluate actual progress with cross-Prompt/same-image and same-Prompt/history-change tasks, unseen whole recordings/scenes, obstacle-induced safe replanning, useful multi-step progress and actual closed-loop completion. Include current-only, shuffled/reset history and stale/no-feedback controls. Measure failures/abstentions, zero-visibility specificity, wrong-object/unsupported GPS claims, latency/deadlines, achieved route and energy/return reserve. Parser acceptance, opaque-ID copying or more receipts are not semantic task accuracy. The r4 single-class auxiliary visual training and the small grounding LoRA experiment cannot establish autonomous reasoning; the LoRA's negative-specificity/ID regressions block promotion despite actual optimizer updates and separate reload proof.

Reuse the same Prompt/RGB/state/history request, typed model output, source/current admission, compiled geometry and measured feedback contracts for SIM and Jetson. Sensor transports, clocks/calibrations and PX4 link adapters differ and need their own actual evidence. Model inference need not run at the flight-controller control-loop rate: PX4 executes the accepted bounded segment while the host observes continuously and prepares the next useful decision. Real Jetson latency, deadline containment, calibrated energy/clearance and whole-sortie physical safety remain separate acceptance work.

## Incremental versus from-zero

Choose incremental integration **at the measured transport/physical-safety boundary**, and replace historical semantic constraints where necessary. Retain actual capture formats, PX4 command semantics, strict clock/identity joins, model weights with proven usefulness, response validation, canonical compilers and replay tooling. Add real multimodal observations and causal action feedback. Do not preserve the r33 feature count, fixed registered task, color categories or full-sortie-per-move compiler as product requirements.

A from-zero flight/model stack discards working sensor/lifecycle/transaction evidence and still needs exactly the same missing clearance, repeated lineage, return supervision and training outcomes. It is justified only if a demonstrated interface limitation prevents the live integration, not because the existing tests look complex. The present biggest blockers are **missing live call sites and missing measured coverage/outcome data**, not a lack of another policy schema.
