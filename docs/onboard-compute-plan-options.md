# 机载算力分配方案（单目、无测距仪，Jetson Orin Nano 8GB）

2026-10-16。前提：飞机只有一个相机，没有测距仪、双目或激光；机上已经要跑快系统（YOLOE 候选框）和慢系统（2B 视觉语言模型，一次只驻留一个）。本页把早期做的单目测距算法放进来一起测算，给出三个可选方案。标“实测”的是开发机或历史 Jetson 上测过的数字，标“估算”的必须在 Orin Nano 上复核。

## 早期单目算法能复用什么

| 模块 | 实际作用 | 需要什么 | 算力 | 证据 |
|---|---|---|---|---|
| `rgb_slam_range.py` | 不是完整 SLAM，而是“用 Pixhawk 位移当基线，多帧射线三角化”给目标测距，有真实尺度 | 稳定的目标跟踪、Pixhawk 位置/姿态、≥0.15 m 基线、射线夹角 ≥0.12° | 纯 CPU，几何最小二乘，估算每目标 < 几毫秒 | 只有合成轨迹单测（相对误差 3% 内），没有 SIM 精度统计 |
| `visual_inertial_range.py` | 同类三角化 + 按物体大小粗测距（运动不足时兜底） | 同上；尺寸先验很宽 | 纯 CPU | 单测级 |
| `multimodal_ranging.py` | 多来源融合：平地/高程图/尺寸/三角化/深度，按新鲜度和不确定度加权，3.5σ 一致性检查 | 相机标定、姿态 | 纯 CPU；历史 Jetson 几何基准中位 0.52 ms | 新闭环已复用它的相机射线几何 |
| `metric_depth.py` | Depth Anything V2 Small 单目深度（室外版标定上限约 80 m） | 预置 TensorRT 引擎，518×518 输入 | GPU，历史 Jetson 实测 68–82 ms/次，设计为约 5 Hz 异步 | 只有 3 帧回放 RMSE 2.5 m，没有飞行精度统计 |
| `monocular_acceptance.py` | 光流外扩 / 碰撞时间（TTC）提示，不给距离 | 320 宽灰度图 | CPU，历史 Jetson 实测 P95 8.3 ms（约 130 Hz） | 合成纹理验证 |
| `attitude_camera_motion.py`、`navigation_fusion.py`、`adaptive_ranging.py` | 旋转补偿、速度融合、来源权重 | Pixhawk | CPU，可忽略 | 单测级 |

关键事实：
- 单目画面本身没有尺度；尺度只能来自 Pixhawk 的位移、已知物体大小或地形数据。三角化在悬停、纯转向、目标移动时会失效，失效时必须退回现有方法。
- 现在的定位（相机射线与地面相交）在平地 SIM 回放里平均误差 2.3 m、P95 8.3 m；在合成坡面上 P95 34–176 m。三角化的价值主要在坡地和没有高程图的地方，以及绕飞检查时（天然多视角）。
- 单目避障只能做“提示”（前方在快速逼近、该减速/悬停），不能承诺绝对距离。现有深度栅格在 SIM 里 F1 只有 0.30–0.34。安全底线仍是静态地图、任务包里的作业高度/范围和 PX4 自身的保护。

## 时间分片（三个方案共用）

飞机是“走走停停”地思考：慢模型判断时悬停，所以 GPU 可以按飞行阶段轮流用。

| 阶段 | GPU | CPU |
|---|---|---|
| 起飞前 | 规划模型编计划（估算 4–6 s，一次），然后卸载、换身份模型 | 任务包与安全检查 |
| 搜索 | YOLOE 每帧（估算 50–90 ms，10–20 Hz） | 跟踪、20 Hz 飞控指令、测距几何 |
| 判断（悬停） | 慢模型一次判断（估算 0.6–1.0 s），YOLOE 降到 2–5 Hz | 同上 |
| 接近 / 绕飞 | YOLOE | 三角化测距（绕飞时视角最好） |
| 返航 | YOLOE 可降频 | 导航、安全 |

## 三个方案

### 方案 A：只加“几何测距”（推荐先做）

- 增加：运动三角化 / RGB-SLAM 测距 + 已知尺寸兜底，用 `multimodal_ranging` 与现有地面相交结果融合；可选光流 TTC 提示（只提示，不接管飞控）。
- 不增加任何新模型，不占 GPU。
- 内存：几乎不变，约 4.7–5.7 GB（估算），余量 2.3–3.3 GB。
- CPU：每个跟踪目标估算 < 5 ms；光流提示 320 宽约 8 ms/帧，可限 10–15 Hz。
- 收益：坡地、无高程图时目标定位明显改善（需离线评估证实）；绕飞检查时定位更准。
- 风险：三角化在悬停、纯转向时无输出，此时退回现有方法。

### 方案 B：几何测距 + 按需单目深度

- 在 A 的基础上，只在“低空接近 / 下降 / 绕飞”阶段开 Depth Anything V2 Small（TensorRT FP16，约 5 Hz），尺度由三角化或已知尺寸校准；慢模型判断时暂停深度推理。
- GPU：深度每次约 70–80 ms（历史 Jetson 实测），这些阶段 YOLOE 会从 10–20 Hz 降到约 8–12 Hz（估算）。
- 内存：多 0.3–0.5 GB（估算），约 5.0–6.2 GB，余量 1.8–3.0 GB。
- 收益：接近和低空时多一个距离来源，以及障碍物“提示”栅格。
- 风险：深度精度证据很弱；GPU 争用让快系统变慢，小目标可能漏帧；发热。

### 方案 C：全程深度 + 深度避障 + 单目地形拟合

- 深度全程 5–10 Hz，深度栅格参与避障，单目运动估计地面高度替代高程图。
- 内存约 5.5–6.7 GB（估算），余量只有约 1.3 GB；GPU 持续三方争用；发热和功耗最大。
- 不推荐：现有证据不足以支撑，且挤压快系统和慢系统。

## 无论选哪个，都要先做

1. 离线评估（不碰机上代码）：用已有 SIM 录像（主仓库 `artifacts/datasets/onboard-loop/`，有 RGB、位姿、内参、深度和真值）比较“平地 / 高程图 / 已知尺寸 / 三角化 / RGB-SLAM / 融合”的定位误差、有效率、不确定度是否可信和每帧 CPU 耗时，按坡度、距离、基线分桶；方案 B 再加深度模型的误差。
2. Orin Nano 真机基准：`scripts/bench_orin_onboard.py` 把上面所有“估算”换成实测。
3. 接入闭环时一律默认关闭、失效自动退回现有方法，SIM 闭环验证后再打开。

## 评估之后的修订（2026-10-16）

离线评估（`docs/onboard-ranging-reuse-eval.md`）改变了方案 B 的重点：

- **步间三角化**（每一步一帧，用不同位置看同一目标的视线交会）是最有效的单目测距：P95 4.45 m，不依赖地面高度，CPU 每次 0.05–0.10 ms，不占 GPU 和内存。
- 早期 RGB-SLAM / 视觉惯性测距需要连续视频才能评价，现有步进录像评不了。
- 单目深度只在 10 m 以内准（10–20 m P95 约 10 m），近距离样本太少，证据不足。

因此方案 B 拆成三个可选的落地方式：

| 选项 | 内容 | 机上代价 | 证据 |
|---|---|---|---|
| B1 几何为主 | 步间三角化 + 平地/高程图融合（地面越不确定越少用平地），接近/绕飞阶段用；深度模型不上机 | CPU < 1 ms/步，内存不变（余量 2.3–3.3 GB），GPU 不变 | 离线评估支持 |
| B2 几何 + 近距深度 | B1 + 只在 < 10 m 的低空接近/下降/近距绕飞开深度（约 5 Hz，判断时暂停） | 多 0.3–0.5 GB 内存；这些阶段 YOLOE 变慢 | 近距离只有 3 个样本，证据弱 |
| B3 原方案 B 不变 | 几何 + 低空接近/下降/绕飞阶段都开深度（含 10–20 m） | 同 B2 | 10–20 m 误差 P95 约 10 m，不达标 |

三种都一样：默认关闭、失效退回现有地面相交；仿真可用后要补录连续视频，再评 RGB-SLAM/VI 和深度。
