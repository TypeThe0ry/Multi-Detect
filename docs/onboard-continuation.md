# OnboardAI 在空中连续改变路线

这项功能解决的是：无人机已经起飞后，AI 看见新情况，要能从现在的位置继续飞下一段，
而不是每做一次判断都重新安排一整次起飞和降落。它仍是同一任务、同一模型和同一架飞机。
最终目标是让用户不需要把“往左看看，再往右看看”逐条输入。

## 本阶段的实现边界

开发路径使用独立、可识别的 continuation 编译契约，复用当前任务校验和 PX4 Mission
编码，不把旧完整架次的 wire 删除几项后继续冒称原来的计划。首版只针对多旋翼，
固定翼和 VTOL 的飞行约束不同，不能直接套用。
当前软件路径只核验原已注册任务和编译配置下的局部移动意图，尚未自动接到在线
推理 scheduler；也没有把它宣称为任意自然语言任务都能执行。

一个航段表达为“当前实测位置 → AI 选定的固定目标 → 有限驻留”。没有新的起飞、
回 HOME 绕行或降落项。模型原回答、画面时间和目标位置保留；飞机移动后，主程序只
重新计算怎样到达那个既定位置，不替模型重新选择目标。显式 Mission cursor 是目标
航点的序号，不从起飞项重新开始。

预算仍计入回 HOME、降落和安全余量，另计爬升／下降、驻留与等下一次推理的时间。
当前参数是开发阶段的保守估计，不是经 Jetson、机体或电池实测标定的续航保证；
预算中的等待上限也不等于已经实现了运行中的超时返航器。

只有“高度大于零”不能证明飞机正在空中。准入需要同一个飞机、任务、HOME、模型
会话和时钟下的原始接收证据：armed 状态、AUTO.MISSION、in-air、父 Mission 当前
序号、实际位置／相对 HOME 高度，以及已提交并读回的父任务记录。哈希用于查验
字节是否变化，不代表消息来源已经认证；真实 receiver 的信任配置必须由主机决定。

只确认 Mission 字节相同还不够：相同任务 ID 可能有不同目标要求，安全配置改变后也
可能生成相同航点。因此另保留原主机编写 Mission 时的声明，逐项绑定完整任务、完整
编译与安全配置、原位置快照、父 Mission、事务记录和共享模型身份。声明默认不受信，
消费前重新查验原字节；不会把旧算法契约的 hash 冒当实际配置的 hash。当前完成的是
这套身份校验的软件实现，真实主机生成和认证声明的链路仍未接通。

目标航段还需当前、覆盖完整三维路线和驻留范围的净空证据。默认没有受信 producer
时不能通过；前方一个测距值或离线夹具不能代替它。飞控实际的
`MIS_TKO_LAND_REQ` 必须确认允许不带起降的 Mission，不能偷偷改参数来让测试通过。

接收子 Mission 时，PX4 实际读回报文指向发起查询的地面站，`current` 位表示其当前
执行序号；它们与上传报文不同。现在先核验实际发送方、注册地面站、事务和 cursor，
保留原接收字节，再只在内容比较副本中处理收发方向和 current 位。航点、参数、高度、
坐标及浮点 wire 精度仍逐项核验，旧上传契约不改。依据是
[PX4 官方任务报文实现](https://github.com/PX4/PX4-Autopilot/blob/main/src/modules/mavlink/mavlink_mission.cpp)。

## 为什么还要做 PX4 实际替换验证

PX4 支持空中上传 Mission，但上传不是执行成功。新航段必须经过暂停、上传、读回、
提交／许可、设置并确认 cursor、恢复 AUTO.MISSION，再从真实遥测证明飞机执行了
它。连续多次改变路线要形成父子链，不能一直引用第一次起飞的旧任务。用户取消、
人工接管、危险或写入状态不确定时不得继续恢复。现有替换事务骨架不是已经接通的
真实 PX4 transport。

这一段飞完仅叫“航段完成”，不等于任务完成、找到目标或已经返航落地。真正的任务
结束仍需匹配证据、返航／降落及新鲜落地解除武装事实。持续空中等待还需要主机的
超时／返航监督器。

这些区别来自 [PX4 多旋翼 Mission 官方说明](https://docs.px4.io/main/en/flight_modes_mc/mission)：
已在空中时 TAKEOFF 会作为航点处理，缺 LAND 的 Mission 结束后会保持在空中；暂停
期间重新上传会改变当前任务序号。因此旧编译器的主要风险是引入 HOME 航点和终端
降落，而不是能断言每次都会重新起飞。有限驻留使用
[MAVLink NAV_LOITER_TIME](https://mavlink.io/en/messages/common.html#MAV_CMD_NAV_LOITER_TIME)。
本项目仍需对固定的固件、参数和真实反馈逐项验证，不能仅依据文档宣称执行已通过。

## 完成训练闭环需要什么

1. 恢复可用、有真实图像的 Gazebo/PX4 运行环境。
2. 同一次运行保存 RGB、实际 HOME、时钟、位置、状态、原模型回答与执行回执。
3. 接通上述 Mission 替换和接收回流，证明连续两个航段仍保持空中执行。
4. 独立审核完整任务轨迹，区分“想做”“获准”“确实执行”“任务完成”。
5. 用这些真实因果轨迹做动作微调，按隔离场景和完整架次留出评估；未通过则不晋升。

不能用相机动画、颜色标签、JSON 或编译成功代替这五步。已有公开 VLM 和世界模型
研究仍用于模型能力与训练方法，不会自动获得飞行权限；当前默认模型不变，
`0.3.0-pre.8` 和 HIL／REAL／Jetson／室外 GNSS／最终发布门保持未通过。
