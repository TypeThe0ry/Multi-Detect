# OnboardAI 下一步：到另一条路线还能不能选对动作

2026-10-08。目标不是让程序按固定路线表飞，而是让同一个机载模型根据用户任务和当前画面，
判断下一段行动；执行后得到新画面，再继续判断。Gazebo 与 Jetson 最终要运行同一套模型和
动作含义。这里记录这条路线当前的一项离线检查，不是已经完成自主飞行。

## 当前实际在做什么

现有导航模型正在本机 GPU 上继续训练，使用原来保存的模型和原来的86条真实图像样本。
这次最多267次新尝试，之前失败消耗的13次另记，累计预算280；不是重新训练一套无关模型。
每8次完成更新保存一个检查点，但只有完整训练、最终输出与新进程重载都结束后，才验收本轮。

新的82条原始三维场景图像已形成独立开发数据，和正在训练的86条分开保存。按事先声明的
路线角色，其中23条留在训练侧，17条用于开发验证、42条用于开发测试。这次只拿后59条
检查最终候选，不把那23条送进模型，也不临时把评估答案拿去训练。

这59条的原始来源属于发布者的TRAIN分区，只是本仓库内部的跨场景开发检查，
**不是官方未知场景测试，也不能独自授予模型飞行资格。**

## 模型到底看见什么

模型只看原任务文字、当前RGB和至多一张最近过去的RGB；输入是真实保存的原图，
不是“红车／绿车”文字脚本，也不是在输入里告诉模型正确方向。

原始姿态、后续画面、动作答案和数据划分留在模型外。模型产生的原始文字、真实生成token、
当前图像身份和实际输入先保存，整轮原始预测都落盘后才与答案比较。不能删字段、改符号、
补零、重试直到正确，或把宿主写出的JSON冒充模型生成的文字。

## 这次能发现什么问题

实际59条包含54前进、1右转、1上升、1下降和2停止。程序分别检查：

- 输出是不是完整、严格合格的动作，而不只是语法能解析的JSON。
- 方向是不是对，米制位移和弧度转角误差有多大；未知数值仍保持未知。
- 停止是否被错误猜成继续前进。这里的停止仅是原导航序列停止，不表示找到目标、返航或降落。
- 生成是否触及192-token上限或超过30秒。原始结果保留作诊断，但预算不合格的结果不计入
  “预算内可用结果”；30秒是生成器的合作式时限，不是已实现的硬实时截止。

当前训练数据只教过前进、左右转和停止，没有教上升／下降。这两条开发样本会暴露这种
能力缺口，不能因为评分程序支持升降，就声称模型已经学会了三维机动。左转、横移、混合
位移和未知量只有软件测试覆盖，实际59条没有对应样本，不能写成模型实测通过。

所有实际位移标签仍为3米、转角为30度。这轮不能证明任意距离、任意转角或完整任务判断。

## 在真正加载候选之前必须完成的事

先完成当前267次训练和最终86条训练内推理，再由另一个实际进程重新加载保存的候选。
核对保存参数、输入和原始输出，确认不是只留下一个文件名或拿内存里的模型代替重载。
审计还要检查更新日志、全部周期检查点、原始来源前后是否一致，并保留之前的失败和预算账。

只有上述终态证据真实存在，新的59条评估才允许产生计划、加载候选。终态缺失或失败时
必须拒绝，不推测“训练应该快好了”，也不自动重启、覆盖已有结果或切换默认模型。

## 不能把这个结果叫作实时飞行

这批历史图像没有可核实的采集时钟，因此本轮不伪造拍摄时间来满足实时请求。
生成耗时不等于相机曝光到飞行执行的总延迟；检查完整生成前缀的观察开销也要明确保留。
旧模型在86条训练样本上的基线仅复用已保存的原始记录，不是新59条上的成对收益对照。

离线检查之后，下一步才是可见的Gazebo三维闭环：从真实渲染相机取新画面，让模型选行动，
通过PX4执行并取得行动反馈，再送回新画面。还要补足真实的转向、垂直行动、安全停止、
连续任务、返航和报告能力，以及Jetson上的实际延迟、内存和同模型运行验证。
不靠固定颜色流程、场景真值或默认方向填补模型能力。

## 当前证据状态

新的离线入口和测试已完成，83项纯软件测试由作者与主智能体分别通过，Ruff检查通过。
测试使用小文件和模型／processor替身，没有执行这59条的实际GPU推理。
当前完整训练、新进程重载和59条模型结果仍待完成；默认模型与版本保持不变。

质量晋升、飞行执行授权、SIM／REAL一致性、Jetson、HIL／REAL、室外GNSS与最终发布门
仍未通过。最终选择继续生成动作文字、增加学习型动作头，还是迁移到公开导航模型，
应依据实际质量、延迟、迁移成本和验证结果，不以已经写过多少代码为理由。
