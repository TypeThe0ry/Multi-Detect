# 从导航模型输出到连续自主飞行

## 用户最终得到什么

用户输入一次任务。OnboardAI持续读取当前和最近过去的相机画面，决定下一段怎样行动；车辆、障碍或飞行状态变化后，重新判断，而不是按预写的“左、右、前进”脚本走到底。

模拟和实机使用同一份训练产物、同一输入含义和同一动作协议。Gazebo提供真实三维渲染画面和传感器观测；Jetson读取真实相机与飞控观测。模型决定动作，PX4负责稳定飞行，执行层核对动作在当前状态下能否安全执行。

这不是把视频生成模型当飞行物理模拟，也不是把一份静态任务解析称为实时自主推理。

## 当前已经做到哪里

- 共享导航Actor已实现：输入只有原任务、当前RGB和至多一张最近过去RGB。训练标签、未来路线、姿态/GPS真值不进入这套模型消息。
- 旧导航LoRA确实完成过86次更新和保存；原失败与后续独立精确重载的边界保留。
- 新均衡续训改为单样本按需编码，287项实现测试及官方CPU86阶段通过；完整GPU对照已退出0。旧LoRA格式69/86、动作55/86、尺度0/86，左／右／停止没有正确完成。随后13次正式更新返回／同步完成，但下一条输入来源校验触发主机MemoryError，worker与监督器均退出1；新候选未保存／重载，不能宣称模型质量改善。旧来源终态验证未完成，不据此声称来源发生漂移。
- 多场景获取/划分工具完成了46项预检测试；实际获取却在第一个指定目录发现只有pose、没有RGB，原生退出1。现有原图仍只有一个训练场景，正在另做有界元数据核查；缺图不能被当成独立测试数据。
- 官方新格式中三条既定原train路线的精确Parquet与pose/config共约53.49MiB已实际获取，27项测试及真实CPU阶段退出0；schema和82metadata行与原pose精确匹配。随后82张原始PNG完整性／解码／来源链核验和实际提取退出0，35项测试通过；下一步动作几何和独立数据划分仍未验收。旧缺图失败及新计划首次序列化失败各自保留，不改写。
- 新导航推理请求/结果协议和预加载实验backend已实现，分别通过158项和89项纯软件测试。加上CPU证据与文档检查，本轮270项通过。它不加载权重、不产生飞控指令，也不替换默认模型；真实processor/model推理仍待验收。

这批标签还有尺度限制：70条前进全部为3米，6条左转和7条右转全部为±30°，另有3条停止，没有未知尺度或升降样本。280次均衡曝光不会增加尺度多样性，训练内结果不能证明模型学会任意距离、任意方向或全任务判断。未来若完整JSON生成不满足实时目标，可以比较在同一底座与现有LoRA上增加学习型动作头；是否改路线要以实际延迟、独立质量和迁移成本决定，当前冻结训练计划不变。

模型选择依据见[通用模型查验](onboard-pretrained-model-options-20261007.md)、[已训练导航模型查验](onboard-pretrained-navigation-model-options-20261008.md)，本轮真实运行见[均衡续训状态](onboard-navigation-balanced-continuation-plan-20261007.md)。

## 接线方案：保留有用接口，移除不适合的旧假设

当前旧VLM worker要求`response/reason/confidence`，而导航LoRA输出的是位移、转向或停止。不能替模型补造confidence，也不能把所有动作包装成旧协议中的SEARCH。

现有空中continuation可以在已起飞后接下一段位移，比每次模型推理都重新编译完整起飞/降落任务更适合连续行动。不过现有实现不接原地yaw，拒绝零水平位移；不能把它描述成已经支持全部导航动作。

新增实验链为：

```text
原任务 + 当前/最近过去RGB
  → 同一导航Actor与精确加载的导航LoRA
  → 原始输出 + 实测token/耗时 + 严格导航结果
  → 原始观测状态/最新状态/任务范围的执行前核对
  → 可支持的下一段空中行动
  → PX4回读与行动反馈
  → 新画面，再次推理
```

严格请求/结果与预加载实验backend已完成软件验证，不改旧worker默认协议。接下来复用已有精确权重加载能力，但不能把加载器的文件SHA声明当作模型实际参数的证明；还要由独占worker管理模型生命周期和真正的进程超时。之后做源帧锚定、dry-run编译；真实连续执行仍要接清障观测和事务生命周期。新能力通过真实SIM验收后再讨论默认模型切换。

实验backend只处理Actor输入前缀，不运行训练答案编码。它保存原始输出、实际生成token、前缀与耗时，拒绝过期画面、耗尽token上限、模型身份不匹配和持续的adapter状态漂移。软件测试中的processor、tensor和model是纯Python替身，不是实际模型验收。停止仍不表示到达或返航，未知位移仍不补成动作。adapter状态复查也不能代替worker独占模型，更不能证明瞬间切换后恢复没有发生。

## 动作含义不能偷换

| 模型输出 | 含义 | 当前接线边界 |
| --- | --- | --- |
| `translate` | 机体前/右/下方向的米制位移 | 必须用源帧姿态转到世界坐标；已知且合格的水平位移可继续接既有空中continuation |
| `turn_yaw` | 旋转机头，右转为正，单位弧度 | 不是左/右平移；尚缺经验证的独立转向执行接口 |
| `stop` | 导航序列停止 | 不是已到达、任务完成、降落或返航；飞行器如何保持安全由另行验证的安全执行层负责 |
| `null`位移/角度 | 数值未知 | 不补零、不重复上次动作、不采用固定方向代替模型 |

上升/下降也要有真正的垂直行动接口；不能靠给零水平动作加一个假的侧向waypoint绕过限制。

## 为什么必须绑定原始画面与姿态

模型看图时无人机可能朝北，也可能倾斜或正在转弯。模型说“向前3米”，必须先根据这张图对应的完整姿态和位置，确定一个固定目标；不能只看最新航向，也不能在推理等待后把同一位移再叠加到新位置。

既有Gazebo帧来源已经保留同帧roll/pitch/heading、观测时间、传感器序号及ENU/FLU到NED/FRD转换。后续执行前核对会复用这些真实观测。缺失、过期或质量不合格的姿态/GPS/高度不能靠场景truth或默认值补齐。

请求的来源、时钟、任务范围和模型身份放在外层绑定中，不混进已经封存的Actor消息。一个SHA只说明内容绑定，不自动证明观测真实性、路径无障碍或飞控授权。

实际接线审查发现：已有`run_external_onboard_model_acceptance._frame_context`可能把同帧经纬度配上最新PX4高度，再标成RGB时间；这不是严格的同帧三维位置。Gazebo现有高度的质量和datum也不自动等于`relative_home`。新导航路径不能复用这种混合观测，必须拿到真正同源的高度及home基准，或明确拒绝。即使机体动作的下向分量为零，完整roll/pitch转换也可能产生世界坐标的高度变化，不能用起飞高度补齐。

## 下一批可验证结果

1. 精确加载导航LoRA，真正使用共享Actor做推理；保留原始输出、tokens、实际输入和延迟，不运行optimizer。
2. 严格解析模型原始动作，拒绝过期、截断、错误模型/来源绑定和未知数值。
3. 在不同场景的原始图像上进行独立验证，旧训练场景及重复画面始终留在训练侧。
4. 源帧锚定的位移先完成dry-run，再通过同一PX4空中事务路径做真实Gazebo闭环。
5. 分别补转向、垂直与安全停止语义，以及完整任务循环、返航与真实报告。
6. 对Jetson与桌面运行做成对验证：模型和动作含义相同，实际引擎、延迟、内存与量化行为另行验收。

当前`quality_claim`、`candidate_promoted`、`execution_authority`、HIL/REAL、室外GNSS、物理性能与最终`0.3.0`发布门仍为false。这里没有声称颜色搜索、悬停、返航或全自主飞行已经由新导航模型完成。

## 实时输出方式也可以重新选择

2026-10-08的流式基线已完整结束，原生退出0：[完整阶段后验回执](evidence/onboard-navigation-streamed-baseline-phase-20261008-r1.json)逐条复算底座与旧LoRA共172条原始输出。关闭导航LoRA时，严格JSON/动作/尺度均0/86，生成平均约7.40秒、p95约8.35秒；旧LoRA为69/86、55/86、0/86，平均约6.34秒、p95约9.16秒。所有合格格式都偏向前进，左转、右转、停止没有正确完成，匹配前进的位移也有7米或97米误差。这是训练样本重代入，不是独立收益或实时飞行验收；原[partial回执](evidence/onboard-navigation-streamed-base-round-20261008-r1.json)按历史保留。计时在输入移到GPU后开始，不能当作从相机曝光到动作执行的总延迟，CPU编码及vision/prefill/decode的分别耗时也未测。

接下来的选择要围绕“及时给出正确下一段动作”，而不是保护某种输出文本：

| 方案 | 用户目标上的收益 | 尚需验证 |
| --- | --- | --- |
| 保留现有LoRA生成动作JSON | 直接复用当前训练产物；推理只处理可观察输入，不再构建训练答案 | 独占常驻worker、真实端到端延迟、输出质量；已有KV缓存不是新增优化 |
| 同一底座和现有LoRA，增加学习型动作/尺度头 | 一次看图后直接预测行动，省去逐字生成完整JSON；宿主只负责按契约包装，不决定动作 | 新head必须实际训练和精确重载；视觉与输入计算仍在，不能预先承诺实时 |

第二种不是新造一个固定决策表。方向、距离与停止判断仍来自训练后的模型；已有YOLO、跟踪和PX4稳定飞行能力继续复用。但当前常数尺度标签不足以训练可靠的任意距离决策，两种方案都需要新的多样化数据和独立评估。

新实验可以建立更合适的误差分布和物理可用性指标，同时保留旧严格评分作公平对照，不能把换评分方式写成旧结果变好。当前280次计划保持冻结；先完成既定对照，再用同一输入实测两种路径的质量、延迟和总内存，决定是否迁移。

训练吞吐也要单独检查。静态源码确认当前流式每次取样把`session=None`传给编码器；Actor与监督目标分别创建完整来源验证会话，都校验并解析大型原记录。它保证当前输入一致，但可能产生重复CPU工作。下一轮先拆开来源校验、图像处理、H2D和模型计算计时，再尝试单样本共用一个成功闭合的验证会话；不跨optimizer步骤消费未完成的验证结果、不缓存全部图像张量，也不修改本轮冻结入口。这里尚未实测节省多少时间，不能把日志间隔当成这一部分的计时。

本轮随后真实失败：[关闭后的训练证据](evidence/onboard-navigation-streamed-training-failure-20261008-r1.json)。13次正式更新返回／同步完成，第14条输入的Actor来源验证会话退出时，`stream.read(1MiB)`触发主机MemoryError，尚未进入本draw的forward或optimizer。监督器和worker均退出1，没有保存候选。源码中该最终校验发生在返回的decoded PIL图像关闭之前；这是生命周期改进点，不是主机内存错误根因已经得到证明。新试验应只为当前样本建立一个共享会话，图像和目标编码结束、会话校验成功退出后才交给loss，并单独测量主机内存；不能重用失败会话或取消来源验证。未保存的13次更新无法作为精确恢复起点，新训练预算必须明确记录已消耗次数，不自动重放280次。

后续输入恢复已完成一次真实官方CPU配对诊断：[恢复说明](onboard-navigation-input-lifecycle-recovery-20261008.md)、[封存证据](evidence/onboard-navigation-closed-sample-cpu-profile-20261008-r1.json)。5个原样本、旧→新各一次，共10次编码完整metadata一致，5次闭合来源验证通过、192来源不变；旧32.58／新16.74秒只是这批固定顺序的inclusive输入编码观察，不是推理延迟、内存收益或GPU故障根因证明。NEW267预算合同已实现，但实际来源计划、完整CPU86与新训练runner/journal仍未通过，没有恢复训练或改变模型／飞行默认。
