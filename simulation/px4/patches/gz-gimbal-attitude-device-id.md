# Gazebo gimbal status device ID candidate

This is a **source patch candidate**, not a built or accepted simulator image.
It adds the existing `_gimbal_device_id` (1) to the status generated by the
Gazebo bridge. It does not authorize mapping arbitrary device ID 0 to ID 1 in
real or simulated MAVLink clients.

## Binding and evidence

- PX4 source commit: `83c4f4e580558816f0e398918f66358988004696`.
- Existing lockstep patch SHA-256: `43bfe32d5d7572b866b3d411c2394d941b6bcc8e19ace5bdd6e230845cdf0559`.
- Existing candidate runtime contract: `simulation/gz-transport/runtime-image-contract.json`, with PX4 binary SHA-256 `9c2280e005ad426f01cdffddf2114e1e4b13e26aa9f5996c4b52cdfa9e722d99`. This patch changes that binary; the existing receipt and image identity must **not** be reused for the modified binary.
- New patch `gz-gimbal-attitude-device-id.patch` SHA-256: `f5c5d6caca92fd04f09e4cf2323b3ba2ab4859e545542a4a163e40721c9d5d13`.
- The pinned `GZGimbal.hpp` declares device ID 1. `publishDeviceInfo()` emits that ID; `OutputMavlinkV2` reads the device information, and manager status publishes the resulting device ID. `publishDeviceAttitude()` zero-initializes its status but, before this patch, never assigns its device ID. The pinned MAVLink stream copies the uORB field unchanged. The two streams use the PX4 MAVLink sender identity, determined by the configured PX4 system/component IDs.
- In the frozen 8056 episode, 204 manager statuses have ID 1 and 2,042 device-attitude statuses have ID 0. The old collector did not record MAVLink header source IDs, so those files do **not** establish the source sysid/compid of either stream. The updated collector records both header fields for future verification.
- MAVLink specifies IDs 1–6 for a device sharing a component with its manager. ID 0 identifies a device with a separate component, whose source component ID is used for association; see [MAVLink common messages](https://mavlink.io/en/messages/common.html#GIMBAL_DEVICE_ATTITUDE_STATUS) and the [gimbal v2 mapping](https://mavlink.io/en/services/gimbal_v2.html#mapping-from-gimbal-managers-to-gimbal-devices).

These are source-level checks; they do not compile PX4 or prove a MAVLink wire message.

Build from a separate pinned checkout with both independently hashed patches, produce a fresh image and content-verification receipt for the new PX4 binary, and preserve the current candidate image and receipt. In the new run record and verify header sysid/compid for both manager status and device attitude, manager device ID 1, status device ID 1, fresh feedback after the commanded movement, and matching physical joint motion. A single gimbal smoke, the two failed hydrant cases, and the full 21-task-by-two acceptance must be independently run and assessed. No successful flight, release, or performance claim follows from this source patch.
